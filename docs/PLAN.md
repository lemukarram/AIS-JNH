# PROMPT FOR CLAUDE CODE — "SENTRA" COMPUTER-VISION DEMO PLATFORM

> Paste everything below this line into Claude Code, in an empty project folder.
> Before you start, optionally put 5 short stock videos (720p, 15–40 s, CCTV-style / top-down / wide angle) into `/source_videos/` named `cam1.mp4` … `cam5.mp4`. If you don't, the build must still work (see §6, Pipeline C).

---

<role>
You are a principal product designer + senior full-stack engineer who has shipped security/analytics control-room software (think Genetec, Verkada, Avigilon-class products) and hand-crafted design systems. You build interfaces that look **designed by a studio, not generated by an AI**. You care about craft: spacing, motion, typography, empty states, micro-interactions, real-feeling data.
</role>

<mission>
Build **a fully working sales-demo web platform** that presents our computer-vision solution for **cafés, restaurants and hospitals**. It must look and behave like a production, real-time CV system that is "already integrated with the client's CCTV cameras and running real-time or post-processing". We take it to client meetings to win pilots and capture leads, so the first 10 seconds must be impressive and every screen must hold up when the client clicks around freely.

It is a **demo product**: video feeds are looped sample footage and the analytics are simulated/pre-computed. Build it so that it is honest and safe to show (see §12 "Demo integrity").
</mission>

<hard_constraints>
**Deployment target: shared PHP / cPanel hosting. This drives every technical choice.**
- PHP 7.4–8.3, Apache + `.htaccess`, MySQL **or** SQLite via PDO (default SQLite so zero setup; MySQL optional via config).
- **No** Node/Python/daemons/WebSockets/Composer-at-runtime/Docker on the server. No build step required on the server.
- Frontend = **vanilla ES modules + modern CSS (custom properties, container queries, `@layer`, `:has()`), no React/Vue/Tailwind/Bootstrap, no CDN dependencies at runtime.** Everything self-hosted (fonts as `woff2`, icons as a hand-drawn SVG sprite, charts hand-built in SVG/Canvas). It must work offline once uploaded.
- Real-time = **client-side simulation engine + lightweight PHP JSON endpoints** (short polling ≤ 5 s where persistence matters). Never SSE/WebSocket.
- Must run from a **sub-folder** (e.g. `https://client-site.com/demo/`) — all URLs relative / base-path aware.
- Total upload size ≤ ~60 MB (compress videos: H.264, `+faststart`, ≤ 3.5 MB each, muted).
- Provide `install.php` (one-time wizard: checks PHP version/extensions/write permissions, creates the DB, seeds data, creates admin, then offers to delete itself) and a `config.php` for branding/demo options.
- Security basics even for a demo: password hashing, CSRF tokens, prepared statements, session hardening, `.htaccess` blocking `/data`, `/tools`, `config.php`, rate-limit on login and lead form.
</hard_constraints>

<design_direction>
**This is the most important part. Use the `frontend-design` skill (and `dataviz` for every chart/stat tile) if available, and commit to a distinctive point of view.**

Concept: **"Quiet control room."** Calm, dense, confident, precise. Dark-first with a true light theme. It should feel like instrument software, not a SaaS template.

Anti-template rules (violations = failure):
- NO purple/blue-pink gradients, NO glassmorphism blur cards, NO generic rounded-2xl card grids with a shadow, NO emoji icons, NO stock-looking gradient hero blobs, NO default system/Inter/Roboto-only typography, NO Chart.js/Recharts look, NO lorem ipsum, no "Dashboard / Welcome back!" clichés.
- Use a restrained palette: deep ink neutrals (≈ `#0B0E11` base, 4–5 elevation steps with *tinted* neutrals), one signature signal color (e.g. electric lime-green `#C6F432` or warm signal amber — pick one and own it), plus semantic colors for severity that pass WCAG AA on the dark surface. Define all as CSS tokens (`--ink-0…--ink-5`, `--signal`, `--ok/--warn/--crit/--info`) for both themes.
- Typography: a characterful pairing, self-hosted (e.g. a grotesk/geometric display for headings + a clean text face + a **tabular, slashed-zero monospace for all numbers, timestamps, IDs, coordinates**). Use `font-variant-numeric: tabular-nums`. Tight, intentional type scale; uppercase micro-labels with letter-spacing for instrument-panel feel.
- Layout: dense but breathable 4/8 px grid, hairline 1 px borders instead of heavy shadows, corner ticks / crosshair details on video tiles, subtle scanline/grain only if it adds meaning (not decoration). Asymmetric layouts where it helps; don't make every page "title + 4 KPI cards + 2 charts".
- Motion: purposeful and fast (120–240 ms, custom easing). Numbers count/roll when they change, alerts slide in with a short highlight, camera tiles "lock on" when a detection appears, page transitions are cross-fades. Respect `prefers-reduced-motion`.
- Details that make it feel built-by-hand: command palette (`Ctrl/⌘+K`), keyboard shortcuts (`1–5` focus camera, `G` grid, `F` fullscreen, `A` alerts, `P` presenter mode), live clock with seconds + server uptime, tooltips with real data, skeleton states, thoughtful empty/error states, consistent focus rings, custom scrollbars, favicon + app title that reflect live alert count.
- Fully responsive: control-room wall (1920+/4K), laptop (1366), tablet (portrait, used in meetings), phone (bottom nav, swipeable camera carousel). Accessible (WCAG AA, keyboard, ARIA live region for alerts, never color-only status).
- **Bilingual EN / العربية with true RTL** (logical CSS properties, mirrored layout, Arabic-appropriate numerals option, correctly shaped Arabic typography with a quality Arabic face, no letter-spacing on Arabic). Language switch is instant and persists. Our clients are in the GCC — the Arabic UI must feel native, not machine-translated.
- Theming per client (**white-label**): product name, logo, accent color, and venue name editable in Settings → Branding and applied live via CSS variables. We will rebrand the demo for each prospect in 30 seconds.
</design_direction>

<information_architecture>
Left rail (collapsible, icon + label), top bar (venue switcher, global search/command palette, live clock, system-health pill, alert bell, language, theme, user menu). Screens:

1. **Login** — cinematic but fast: left = animated mosaic of camera thumbnails with detection boxes, right = form. Demo credential chips ("Admin", "Manager", "Viewer") that autofill. Remember-me, forgot-password (non-functional but polished).
2. **Overview (Dashboard)** — venue-level live KPIs with sparklines + deltas vs. yesterday/last week: people in venue now, footfall today, peak hour, avg dwell time, queue length, avg wait time, table/bed occupancy %, active alerts, cameras online, AI model FPS/latency. Hourly footfall chart (today vs. avg), occupancy gauge, a floor-plan mini-map with live heat dots, top zones list, and a live event ticker. Layout must feel composed, not a uniform grid.
3. **Live Wall** — the hero screen. Layouts: 1+4 "spotlight", 2×2, 3+2, single. **5 cameras minimum** (café: Entrance, Counter/Queue, Seating, Kitchen/Back-of-house, Outdoor/Parking; hospital: Lobby, Waiting Room, Corridor, ER Entrance, Parking; restaurant: Entrance, Dining Hall, Bar, Kitchen, Terrace). Each tile: video + canvas overlay (bounding boxes with track IDs, class labels, confidence %, motion trails, zones and counting lines), top-left camera name + status LED, top-right REC/LIVE badge + FPS + latency + bitrate, bottom strip with per-camera counters (in/out/current), click to expand, double-click for fullscreen, overlay toggles (boxes / trails / zones / heatmap / privacy blur / skeleton). A side panel shows the **real-time alert feed** with thumbnails, severity, camera, and one-click Acknowledge / Escalate / Bookmark.
4. **Alerts & Events** — filterable table + timeline, severity, status workflow (New → Acknowledged → Resolved), snapshot + 5-second clip preview (loop the source video at the event timestamp), assignee, notes, rule that triggered it.
5. **Analytics** — footfall, dwell, funnel (entered → queued → seated → paid, where relevant), zone heatmaps over a floor plan, day/week/month comparison, peak-hour forecast (simulated), demographics-free by design (privacy-first: count/behaviour only, no face ID). Hand-built chart components with brushing, hover crosshair, and export.
6. **Playback / Post-Processing** — pick camera + date/time, scrub a timeline with event markers, speed controls; **"Upload footage for analysis"** simulates a batch job queue (progress bars, stages: ingest → detect → track → analyse → report, ETA, finished jobs open a generated report). This is how we show *post-processing* mode.
7. **Reports** — pre-baked reports (Daily Ops, Weekly Footfall, Queue & Service Level, Safety Incidents, Occupancy Compliance), live HTML preview, **real PDF/CSV export** (client-side print stylesheet + CSV generation; no server libs), scheduled-report UI.
8. **Cameras & Zones** — camera list with health (uptime, packet loss, stream URL field e.g. `rtsp://…`, resolution, codec), "Add camera" wizard (ONVIF/RTSP/NVR choices, test-connection animation), and a **zone/line editor** on a camera frame (draw polygons and tripwire lines, name them, set rules). Zones created here must immediately affect the overlay and counters in the Live Wall.
9. **Rules & Detection (Settings → AI)** — toggle detection modules per venue type, thresholds, schedules, notification channels (email/SMS/WhatsApp/webhook — UI only), retention, privacy (face blur on/off, no-biometrics statement), model selector (display only), sensitivity sliders that visibly change simulated behaviour.
10. **Settings** — Branding, Venue profile & industry preset, Users & Roles (RBAC UI that really hides/disables features per role), API keys & Integrations (POS, HIS/HL7-FHIR for hospitals, WhatsApp, Slack — UI only), Audit log (real, written by the app), System health (CPU/GPU/NPU temp, queue depth, inference FPS, storage).
11. **Presenter Mode** (`P`) — a discreet drawer for the salesperson only: switch **industry preset** (Café / Restaurant / Hospital — swaps cameras, KPIs, alert types, copy, floor plan), **trigger scripted incidents on demand** (queue exceeds threshold, unattended bag, fall detected, restricted-area entry, crowding, spill, staff-absent at counter, no hand-hygiene at entrance), speed up time, reset data, hide cursor/kiosk fullscreen, jump to "wow" screens.
12. **Request a Pilot** — a tasteful persistent CTA + modal/page capturing lead (name, venue, type, number of cameras, phone/WhatsApp, email, notes) → stored in DB → Admin "Leads" view with CSV export. Anti-spam honeypot + rate limit. Optional email via PHP `mail()` to an address in `config.php`.

Industry presets must be deeply different, not a label swap:
- **Café/Restaurant:** queue length & wait time, service-level %, table turnover, occupancy vs. capacity, dwell by zone, staff-at-counter presence, cleanliness/spill, peak-hour staffing suggestions, entrance conversion (passers-by → entered), unattended items, outdoor/parking counts.
- **Hospital:** waiting-room crowding, patient flow by department, restricted-area/zone intrusion, fall/lying-person detection, wheelchair/stretcher in corridor, ER entrance queue, unattended bag, hand-hygiene compliance at dispensers, after-hours movement, parking occupancy.
</information_architecture>

<computer_vision_realism>
It has to look like inference is genuinely happening. Implement **three pipelines, selected automatically by what's available** (build A and C fully; B is a stretch goal behind a flag):

**A — Baked real detections (preferred).** Provide `/tools/bake_tracks.py` (runs on *our* laptop, not the server): reads `/source_videos/camN.mp4`, runs a small YOLO model (e.g. Ultralytics YOLOv8n) + ByteTrack/BoT-SORT for persons (and cups/laptops/bags/chairs/cars where relevant), applies our zone/line definitions, and writes `/assets/tracks/camN.json` (frame-indexed boxes, IDs, classes, confidence, per-track dwell, line-crossing events) plus `/assets/tracks/events.json` (derived alerts). The browser then replays these **frame-synchronised with the video** using `requestVideoFrameCallback` (fallback to `currentTime`), so boxes stick to real people. Include a README with exact commands and a requirements file, and make the tool resilient (CPU-only, progress bar, resume).
**B — In-browser live inference (stretch, behind `?live=1`).** Optional self-hosted TF.js/ONNX-Web COCO-SSD style model running on throttled round-robin frames, with a simple IoU tracker. Must degrade gracefully and never block the UI.
**C — Procedural simulation (always works, zero assets).** A seeded generator draws realistic top-down/wide "camera" scenes on canvas (animated people following believable paths through a floor plan, queue behaviour, seating, doors) and emits the same detection/track schema as A. Used automatically for any camera without video/tracks and for the floor-plan minimap, so the demo never shows a broken feed.

Realism details: per-camera jitter in confidence, occasional track-ID switches/re-acquisitions, FPS fluctuation (e.g. 24–30), latency 80–220 ms, short "reconnecting…" blips on one camera (rare, auto-recover), night/low-light IR look on one feed via CSS filter, timestamp burn-in, camera-ID watermark, and a visible "inference" HUD (model name, ms/frame). All counters (in/out/current) must be **consistent** with the tracks and with the numbers on the Dashboard, Analytics and Reports — one shared state store, no contradictory numbers anywhere.
</computer_vision_realism>

<data_and_architecture>
- Single source of truth: a small client-side store (pub/sub) fed by the simulation engine; PHP persists alerts, acknowledgements, notes, users, settings, zones, leads, audit log and pre-seeded 90 days of historical data (seeded with a deterministic RNG, with believable weekly/daily seasonality, weather dips, promo spikes — not uniform noise).
- Folder layout (suggested): `/index.php` (router + shell) · `/api/*.php` (JSON endpoints: auth, alerts, stats, zones, settings, leads, reports, health) · `/app/` (PHP helpers: db, auth, csrf, i18n) · `/assets/css|js|fonts|icons|video|tracks|img` · `/lang/en.json`, `/lang/ar.json` · `/data/` (SQLite + logs, blocked by .htaccess) · `/tools/` (bake script, video-compress script, seed script) · `/install.php` · `config.php` · `README_DEPLOY.md`.
- JS organised as small ES modules (store, engine, renderer, charts, router, i18n, ui components). No giant single file. Lazy-load heavy screens. 60 fps target on a mid laptop with 5 live tiles; cap overlay redraw to what's visible; pause off-screen tiles (`IntersectionObserver`) and when the tab is hidden.
- Seed accounts: `admin@demo.local`, `manager@demo.local`, `viewer@demo.local` (password shown in README and on the login chips). Roles genuinely gate UI and API.
</data_and_architecture>

<working_method>

2. Build in phases, committing to git after each: (1) design system + shell + i18n/RTL, (2) simulation engine + store, (3) Live Wall, (4) Dashboard + Alerts, (5) Analytics + Reports + Playback, (6) Cameras/Zones editor + Settings + RBAC, (7) Presenter Mode + Leads, (8) PHP backend/installer, (9) bake tool, (10) polish + QA + docs.

6. Performance budget: first contentful paint < 1.5 s on a 4G profile for Login/Overview; Live Wall interactive < 3 s; no layout shift; Lighthouse ≥ 90 on Performance/Accessibility/Best Practices for Overview.
</working_method>
